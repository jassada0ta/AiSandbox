# Manual repo setup guide

How to build this monorepo and all four projects from an empty folder, by hand.

Two audiences:

- **You just cloned the repo** and want it running → do
  [Part 0](#part-0--running-an-existing-clone) and stop.
- **You are rebuilding it from scratch**, or want to understand why a file
  looks the way it does → Part 0 is optional; work through
  [Part 1](#part-1--the-workspace-root) onward.

Everything here was run on Node 22 with npm 10. The versions in the scaffold
commands are pinned so a rebuild lands on the same setup.

---

## Part 0 — Running an existing clone

```bash
npm install          # installs all four workspaces at once
npm run setup        # writes apps/SandboxApi/.env with generated secrets
npm run build        # SPA → SandboxApi/public/app, then proto, then Strapi admin
npm run start        # Strapi on http://localhost:1337
```

Open <http://localhost:1337/admin> and create the admin user (first run only).

Then check the four surfaces:

| URL                                | What you should see                     |
| ---------------------------------- | --------------------------------------- |
| <http://localhost:1337/admin>      | Strapi admin panel                      |
| <http://localhost:1337/app/>       | SandboxSpaApp, reporting "Connected"    |
| <http://localhost:1337/graphql>    | GraphQL playground (in development)     |
| <http://localhost:1337/_health>    | 204, empty body                         |

For day-to-day work use the dev servers instead, which have hot reload:

```bash
npm run dev          # all three at once
```

| App                 | Dev URL                 |
| ------------------- | ----------------------- |
| SandboxApi          | <http://localhost:1337> |
| SandboxSpaApp       | <http://localhost:5173> |
| SandboxPrototypeWeb | <http://localhost:5174> |

And to prove it all works together:

```bash
npm run test:e2e     # builds, boots both servers, runs 15 Playwright tests
```

> **Note on `npm run dev:spa`.** In dev the SPA is served from Vite on port
> 5173 at `/app/`, so the URL is <http://localhost:5173/app/>. Its `/api`,
> `/graphql` and `/uploads` requests are proxied to Strapi on 1337, so request
> paths are identical to production.

## Part 1 — The workspace root

```bash
mkdir AiSandbox && cd AiSandbox
git init
```

The root package is private, never published, and exists to hold the workspace
list and the cross-project scripts. Create `package.json`:

```json
{
  "name": "aisandbox",
  "version": "0.1.0",
  "private": true,
  "workspaces": ["apps/*"],
  "engines": { "node": ">=20.0.0 <=26.x.x" }
}
```

`workspaces: ["apps/*"]` is what makes one `npm install` at the root install
all four projects and hoist their shared dependencies into a single
`node_modules`.

> **Why npm workspaces and not pnpm or Yarn?** npm ships with Node, so a clone
> needs no extra install step. The one real risk was Strapi's admin panel build
> under npm's hoisting — it was tested end to end and works. See
> `specs/0001-monorepo-foundation/plan.md` for the full comparison.

Add `.nvmrc` with `22`, and a `.gitignore`. The one entry that is easy to miss:

```gitignore
# The SPA build artefact that lands inside the Strapi public folder
apps/SandboxApi/public/app/
```

That folder is generated by SandboxSpaApp's build. Committing it would mean
every SPA change shows up twice in review.

Also ignore `node_modules/`, `dist/`, `.tmp/`, `.env` (but not
`.env.example`), `*.db`, `test-results/` and `playwright-report/`.

The scripts come at the end, once the projects exist —
[Part 6](#part-6--the-root-scripts).

## Part 2 — SandboxApi (Strapi, JavaScript)

The backend for the other projects. JavaScript, sqlite by default, with the
GraphQL plugin.

### 2.1 Scaffold

```bash
npx create-strapi-app@5.52.3 apps/SandboxApi \
  --js --no-run --no-install --skip-cloud --no-example \
  --no-git-init --use-npm --dbclient=sqlite --non-interactive
```

Each flag earns its place: `--js` for JavaScript rather than the TypeScript
default, `--no-install` because the root install handles dependencies,
`--no-git-init` because the monorepo owns the repository, `--no-example` to
skip the sample blog content, and `--non-interactive` so no prompt appears.

### 2.2 Add the GraphQL plugin

```bash
npm pkg set dependencies.@strapi/plugin-graphql=5.52.3 \
  --prefix apps/SandboxApi
```

Keep the version in step with `@strapi/strapi`; the Strapi plugins are released
together and a mismatch fails at boot.

Then configure it in `apps/SandboxApi/config/plugins.js`. The scaffold already
exports a function — change its signature to take `{ env }` and add the
`graphql` key:

```js
module.exports = ({ env }) => ({
  graphql: {
    enabled: true,
    config: {
      endpoint: '/graphql',
      shadowCRUD: true,
      depthLimit: 10,
      amountLimit: 100,
      playgroundAlways: env.bool('GRAPHQL_PLAYGROUND_ALWAYS', false),
      apolloServer: {
        tracing: false,
        introspection: env.bool('GRAPHQL_INTROSPECTION', true),
      },
    },
  },
  // …the users-permissions and upload config the scaffold wrote stays as-is
})
```

What these do:

- **`shadowCRUD: true`** generates queries and mutations for every content type
  automatically. Add a content type in the admin and its GraphQL surface
  appears with no resolver written.
- **`depthLimit` and `amountLimit`** bound how deeply and how broadly a single
  query can traverse relations. Without them one request can walk a relation
  graph in a loop.
- **`playgroundAlways: false`** keeps the interactive playground to development
  only. Strapi enables it in development regardless; this flag is how you turn
  it on anywhere else, deliberately.

### 2.3 Serve the SPA from `public/app`

Strapi serves `public/` as static files, so a build in `public/app` is already
reachable at `/app`. But `strapi::public` (koa-static) can only serve files
that exist on disk — a client-side route like `/app/settings` 404s on a hard
refresh.

Create `apps/SandboxApi/src/middlewares/spa-fallback.js`:

```js
module.exports = (config = {}) => {
  const mountPath = config.mountPath || '/app'
  const indexPath = `${mountPath}/index.html`

  return async (ctx, next) => {
    const isReadRequest = ctx.method === 'GET' || ctx.method === 'HEAD'
    const isUnderMount =
      ctx.path === mountPath || ctx.path.startsWith(`${mountPath}/`)

    if (isReadRequest && isUnderMount) {
      // Anything with a file extension is a real asset request.
      const looksLikeAsset = /\.[^/]+$/.test(ctx.path)
      if (!looksLikeAsset) {
        ctx.path = indexPath
      }
    }

    await next()
  }
}
```

Register it in `apps/SandboxApi/config/middlewares.js` **directly above**
`strapi::public`:

```js
module.exports = [
  'strapi::logger',
  'strapi::errors',
  'strapi::security',
  'strapi::cors',
  'strapi::poweredBy',
  'strapi::query',
  'strapi::body',
  'strapi::session',
  'strapi::favicon',
  { name: 'global::spa-fallback', config: { mountPath: '/app' } },
  'strapi::public',
]
```

Order is the whole trick: the middleware rewrites `ctx.path`, and
`strapi::public` — running next — serves whatever path it is handed. Put it
below `strapi::public` and it never runs for these requests. The
`global::` prefix is how Strapi addresses a middleware in
`src/middlewares/`.

### 2.4 Fix the environment file

The scaffold writes an `.env` that **cannot boot with sqlite**. It contains:

```
DATABASE_FILENAME=
```

and `config/database.js` does:

```js
filename: path.join(__dirname, '..', env('DATABASE_FILENAME', '.tmp/data.db'))
```

An empty string is a defined value, so the default never applies and sqlite is
handed the project directory instead of a file. Strapi exits with `SqliteError:
unable to open database file`. Sqlite also will not create the directory that
holds its database file.

Both are handled by `scripts/ensure-env.mjs` ([Part 6](#part-6--the-root-scripts)).
To do it by hand:

```bash
# in apps/SandboxApi/.env
DATABASE_CLIENT=sqlite
DATABASE_FILENAME=.tmp/data.db
```

```bash
mkdir -p apps/SandboxApi/.tmp
```

Finally, rewrite `.env.example` so it documents the sqlite and GraphQL
variables — it is the file the setup script generates from, and the only
version of this configuration that is committed.

> **`.env` is git-ignored and holds real secrets.** `APP_KEYS`,
> `ADMIN_JWT_SECRET`, `JWT_SECRET`, `API_TOKEN_SALT`, `TRANSFER_TOKEN_SALT` and
> `ENCRYPTION_KEY` are generated per machine. Never commit them, and never
> reuse a development set anywhere real.

### 2.5 Verify

```bash
npm install                                   # from the repo root
npm run build --workspace apps/SandboxApi     # builds the admin panel, ~25s
npm run develop --workspace apps/SandboxApi
```

Then, in another terminal:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:1337/_health
curl -s http://localhost:1337/graphql \
  -H 'Content-Type: application/json' \
  -d '{"query":"{ __schema { queryType { name } } }"}'
```

You want `204` and `{"data":{"__schema":{"queryType":{"name":"Query"}}}}`.

## Part 3 — SandboxSpaApp (React + Vite)

The single page app, deployed into the Strapi `public/app` folder.

### 3.1 Scaffold

```bash
npx create-vite@9.2.0 apps/SandboxSpaApp --template react
```

`--template react` is the JavaScript one; `react-ts` would be TypeScript.

Then set the package name to `sandbox-spa-app` (npm package names must be
lowercase, so it cannot match the folder — the root scripts address workspaces
by path, which sidesteps this).

### 3.2 The deployment contract

This is the only part that couples the SPA to the API, and it lives entirely in
`apps/SandboxSpaApp/vite.config.js`:

```js
import { fileURLToPath } from 'node:url'
import react from '@vitejs/plugin-react'
import { defineConfig, loadEnv } from 'vite'

const STRAPI_PUBLIC_APP_DIR = fileURLToPath(
  new URL('../SandboxApi/public/app', import.meta.url),
)

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), '')
  const apiTarget = env.VITE_DEV_API_PROXY_TARGET || 'http://localhost:1337'

  return {
    base: '/app/',
    plugins: [react()],
    build: {
      outDir: STRAPI_PUBLIC_APP_DIR,
      emptyOutDir: true,
      sourcemap: mode !== 'production',
    },
    server: {
      port: 5173,
      strictPort: true,
      proxy: {
        '/api': { target: apiTarget, changeOrigin: true },
        '/graphql': { target: apiTarget, changeOrigin: true },
        '/uploads': { target: apiTarget, changeOrigin: true },
      },
    },
  }
})
```

Three settings carry the deployment:

- **`base: '/app/'`** — every generated asset URL is prefixed, so
  `/app/assets/index-abc123.js` resolves when Strapi serves the page from
  `/app`. Leave it out and the app requests `/assets/…`, which Strapi answers
  with a 404 or, worse, its own admin bundle.
- **`build.outDir`** — points outside the package, straight into the Strapi
  public folder. This is what makes "deploying" the SPA just `npm run build`.
  Resolved from `import.meta.url` rather than a bare relative string, so it
  does not depend on the working directory.
- **`emptyOutDir: true`** — Vite refuses to clear a folder outside its own root
  without this. Needed so stale hashed assets do not pile up.

The **proxy** matters more than it looks. It means the SPA can call `/graphql`
with a relative URL in both dev and production, so no code path differs between
the two. That is why `VITE_API_BASE_URL` is empty by default.

### 3.3 Application code

Replace the Vite demo with something real. Two files:

- **`src/api/client.js`** — `restRequest`, `graphqlRequest` and
  `checkGraphqlConnection` helpers over `fetch`, prefixing
  `VITE_API_BASE_URL` (empty by default, so URLs stay relative).
- **`src/App.jsx`** — a page that probes the GraphQL endpoint on mount and
  reports whether the backend is reachable.

Give anything a test will look at a `data-testid`. This app exposes
`app-title`, `backend-status` (plus a `data-status` attribute so a test can
assert the state without matching display text), `backend-detail` and
`retry-backend`. Deciding these in the plan means the e2e tests can be written
before the UI exists.

> **One lint note.** `oxlint`'s `react/set-state-in-effect` rule fires on the
> mount probe. The effect is exactly the "synchronizing with an external
> system" case the rule documents as legitimate, and every `setState` in the
> probe runs after an `await`, so the effect carries a one-line disable with
> that reasoning rather than the code being contorted around the linter.

### 3.4 Verify

```bash
npm run build --workspace apps/SandboxSpaApp
ls apps/SandboxApi/public/app
```

You want `index.html`, `favicon.svg` and an `assets/` folder. Check that
`index.html` references `/app/assets/…` and not `/assets/…`.

## Part 4 — SandboxPrototypeWeb (Vite, vanilla JS)

A host for prototype HTML files. The entry page lists every one of them, and it
must never need editing when a file is added.

### 4.1 Scaffold

```bash
npx create-vite@9.2.0 apps/SandboxPrototypeWeb --template vanilla
```

Delete the demo (`src/counter.js`, `src/assets/`) and create `prototypes/`,
where the HTML files will live.

### 4.2 The scanner

`apps/SandboxPrototypeWeb/prototypes.js` exports `listPrototypes(rootDir)`,
which walks `prototypes/**/*.html` and returns one record per file:

```js
{
  id: 'prototypes/examples/api-fetch',        // Rollup input key
  file: 'prototypes/examples/api-fetch.html',
  url: '/prototypes/examples/api-fetch.html',
  group: 'examples',                          // subfolder, '' at top level
  title: 'API fetch',                         // <title>, else <h1>, else filename
  description: '…',                           // <meta name="description">
  updatedAt: '2026-09-06T…',                  // file mtime
}
```

Reading the title and description **out of each file** is what keeps a
prototype a single self-contained document — there is no sidecar metadata file
to keep in sync, and nothing to register.

### 4.3 Two consumers, one scan

The same function is used twice, which is the whole design.

**At config time**, to give Rollup one entry per file, in `vite.config.js`:

```js
const prototypeInputs = Object.fromEntries(
  listPrototypes(rootDir).map(({ id, file }) => [id, file]),
)

export default defineConfig(({ mode }) => ({
  plugins: [prototypeManifest()],
  build: {
    rollupOptions: {
      input: { index: 'index.html', ...prototypeInputs },
    },
  },
  server: { port: 5174, strictPort: true },
  preview: { port: 4174, strictPort: true },
}))
```

Without this, `vite build` emits only `index.html` and every prototype
disappears from the production build. Vite preserves each entry's path relative
to the project root, so `prototypes/foo.html` builds to
`dist/prototypes/foo.html` and the dev and built URLs match.

**At runtime**, through a virtual module, so the entry page can render the
list. `vite-plugin-prototype-manifest.js`:

```js
const VIRTUAL_ID = 'virtual:prototype-manifest'
const RESOLVED_VIRTUAL_ID = `\0${VIRTUAL_ID}`

export default function prototypeManifest() {
  let rootDir = process.cwd()

  return {
    name: 'sandbox:prototype-manifest',
    configResolved(config) {
      rootDir = config.root
    },
    resolveId(id) {
      return id === VIRTUAL_ID ? RESOLVED_VIRTUAL_ID : null
    },
    load(id) {
      if (id !== RESOLVED_VIRTUAL_ID) return null
      return `export default ${JSON.stringify(listPrototypes(rootDir))}`
    },
    configureServer(server) {
      // …watch prototypes/ and full-reload on add, unlink or change
    },
  }
}
```

The leading `\0` is the Rollup convention marking a module id as virtual, so no
other plugin tries to read it off disk. `configureServer` watches the folder so
dropping in a new file refreshes the list without restarting the dev server.

> **Why not `import.meta.glob`?** It would give the entry page its list in one
> line, but the build still needs the file list to compute
> `rollupOptions.input`. One scanner feeding both is less machinery than two
> mechanisms that can disagree.

### 4.4 The entry page

`src/main.js` imports the manifest and renders it:

```js
import prototypes from 'virtual:prototype-manifest'
```

It then groups by subfolder, renders a card per prototype with title,
description, path and modified date, shows a count, and filters on typing. All
user-supplied strings go through an HTML-escaping helper before being
interpolated into markup — the titles and descriptions come from files on
disk, and escaping them keeps a stray `<` in a title from breaking the page.

The testids the e2e suite uses: `app-title`, `prototype-count`,
`prototype-filter`, `prototype-item`, `prototype-link`, `prototype-group`
(with `data-group`), `prototype-empty`.

### 4.5 Shared chrome and conventions

`public/prototype.css` holds the shared styling. It sits in `public/` so a
prototype can pull it in with a plain `<link rel="stylesheet"
href="/prototype.css">` and stay copy-pasteable, with no build step of its own.

Add `prototypes/README.md` documenting the conventions, then a first page:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <meta name="description" content="What this prototype explores." />
    <link rel="stylesheet" href="/prototype.css" />
    <title>Welcome</title>
  </head>
  <body>
    <div class="prototype-shell">
      <a class="prototype-back" href="/">&larr; All prototypes</a>
      <h1>Welcome</h1>
    </div>
  </body>
</html>
```

Put a second one in `prototypes/examples/` so the grouping is exercised by the
sample content and not only by a test.

### 4.6 Verify

```bash
npm run build --workspace apps/SandboxPrototypeWeb
find apps/SandboxPrototypeWeb/dist -name '*.html'
```

You want `dist/index.html` plus one file per prototype, at the same paths they
have in the source.

## Part 5 — SandboxE2eTest (Playwright)

The e2e suite runs against the **deployed** shape of the system, not the dev
servers: Strapi serving the built SPA, and `vite preview` serving the built
prototype host. Testing dev servers would leave the `/app` deployment contract
— the thing most likely to break — unproven.

### 5.1 Package

Created by hand rather than with `npm init playwright`, which is interactive and
scaffolds its own repo layout:

```json
{
  "name": "sandbox-e2e-test",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "scripts": {
    "test": "playwright test",
    "test:ui": "playwright test --ui",
    "test:api": "playwright test --project=api",
    "test:spa": "playwright test --project=spa",
    "test:prototype": "playwright test --project=prototype",
    "install:browsers": "playwright install --with-deps chromium"
  },
  "devDependencies": { "@playwright/test": "^1.63.0" }
}
```

After `npm install` at the root, download the browser once:

```bash
npm run e2e:install
```

Skip that if the machine already provides Chromium — see the note in 5.2.

### 5.2 Configuration

`apps/SandboxE2eTest/playwright.config.js` does three things.

**Boots both servers.** Playwright starts them, waits for the URLs to answer,
and shuts them down afterwards:

```js
webServer: [
  {
    command: 'npm run start --workspace apps/SandboxApi',
    cwd: repoRoot,
    url: `${API_BASE_URL}/_health`,
    reuseExistingServer: !isCI,
    timeout: 180_000,
  },
  {
    command: 'npm run preview --workspace apps/SandboxPrototypeWeb',
    cwd: repoRoot,
    url: `${PROTOTYPE_BASE_URL}/`,
    reuseExistingServer: !isCI,
    timeout: 60_000,
  },
]
```

`cwd: repoRoot` (from `fileURLToPath(new URL('../..', import.meta.url))`) is
what lets these use the root's `--workspace` scripts. `/_health` returns 204,
which counts as ready. `reuseExistingServer` attaches to a dev server you
already have running locally, but never in CI, where a stale server would
silently test the wrong build.

**Splits the tests by target**, so one run covers three different base URLs:

```js
projects: [
  { name: 'api', testMatch: /tests\/api\/.*\.spec\.js/, use: { baseURL: API_BASE_URL } },
  { name: 'spa', testMatch: /tests\/spa\/.*\.spec\.js/, use: { ...browser, baseURL: API_BASE_URL } },
  { name: 'prototype', testMatch: /tests\/prototype\/.*\.spec\.js/, use: { ...browser, baseURL: PROTOTYPE_BASE_URL } },
]
```

The `spa` project points at the **API** base URL, because that is where the SPA
is actually served from. The `api` project needs no browser at all — it uses
Playwright's `request` fixture.

**Allows an external browser.** Some CI images and sandboxes ship a Chromium
that is not the build `playwright install` would fetch:

```js
const chromium = process.env.E2E_CHROMIUM_EXECUTABLE
const browser = chromium
  ? { ...devices['Desktop Chrome'], launchOptions: { executablePath: chromium } }
  : devices['Desktop Chrome']
```

Unset, everything behaves normally. The alternative — pinning
`@playwright/test` to whatever version matches the image — ties the test
dependency to one machine.

Also set `retries: 2` and `workers: 1` under CI, `trace: 'on-first-retry'`, and
screenshots and video on failure.

### 5.3 The tests

15 tests across three folders, each asserting something the spec asked for:

| File                            | Tests | Covers                                                               |
| ------------------------------- | ----- | -------------------------------------------------------------------- |
| `tests/api/health.spec.js`      | 2     | `/_health` returns 204; `/admin` serves the panel                     |
| `tests/api/graphql.spec.js`     | 3     | Schema introspection, shadow-CRUD types, error handling for bad fields |
| `tests/spa/deployment.spec.js`  | 5     | Mounts at `/app`, assets under `/app/`, route fallback, GraphQL reach  |
| `tests/prototype/index.spec.js` | 5     | Count matches links, every link resolves, grouping, filtering          |

Two are worth copying the approach from.

**Asserting the asset base path** — this is what catches a missing
`base: '/app/'`, which is otherwise invisible until deploy:

```js
page.on('response', (response) => {
  const { pathname } = new URL(response.url())
  if (/\.(js|css)$/.test(pathname)) {
    assetRequests.push({ pathname, status: response.status() })
  }
})

await page.goto('/app/')

for (const asset of assetRequests) {
  expect(asset.pathname).toMatch(/^\/app\//)
  expect(asset.status).toBeLessThan(400)
}
```

**Asserting the index has no stale or missing entries** — it reads the links off
the page and checks each one resolves, so a prototype that is listed but not
built fails here:

```js
const hrefs = await page
  .getByTestId('prototype-link')
  .evaluateAll((anchors) => anchors.map((a) => a.getAttribute('href')))

for (const href of hrefs) {
  expect((await request.get(href)).status()).toBe(200)
}
```

Every assertion holds against a stock Strapi install, so the suite needs no
seeded content and no fixtures.

### 5.4 Verify

```bash
npm run test:e2e     # from the repo root; builds first
```

Expect `15 passed`.

## Part 6 — The root scripts

Now wire the projects together. Add to the root `package.json`:

```json
{
  "scripts": {
    "setup": "node scripts/ensure-env.mjs",
    "predev": "npm run setup",
    "dev": "concurrently -n api,spa,proto -c blue,green,magenta \"npm:dev:api\" \"npm:dev:spa\" \"npm:dev:proto\"",
    "dev:api": "npm run develop --workspace apps/SandboxApi",
    "dev:spa": "npm run dev --workspace apps/SandboxSpaApp",
    "dev:proto": "npm run dev --workspace apps/SandboxPrototypeWeb",
    "build": "npm run build:spa && npm run build:proto && npm run build:api",
    "build:api": "npm run build --workspace apps/SandboxApi",
    "build:spa": "npm run build --workspace apps/SandboxSpaApp",
    "build:proto": "npm run build --workspace apps/SandboxPrototypeWeb",
    "start": "npm run start --workspace apps/SandboxApi",
    "lint": "npm run lint --workspace apps/SandboxSpaApp",
    "pretest:e2e": "npm run setup && npm run build",
    "test:e2e": "npm run test --workspace apps/SandboxE2eTest",
    "e2e:install": "npm run install:browsers --workspace apps/SandboxE2eTest",
    "spec:new": "node scripts/new-spec.mjs",
    "spec:check": "node scripts/check-specs.mjs"
  },
  "devDependencies": { "concurrently": "^9.1.2" }
}
```

Two details that matter:

- **Workspaces are addressed by path** (`--workspace apps/SandboxApi`), not by
  name. npm package names must be lowercase, so they cannot match the
  PascalCase folder names; paths avoid maintaining a mental mapping.
- **`build` order is not arbitrary.** The SPA writes into
  `SandboxApi/public/app`, so it goes first. `pretest:e2e` runs the whole build
  before the suite, so the tests can never pass against stale output.

### `scripts/ensure-env.mjs`

Makes a fresh clone bootable, and is safe to re-run:

1. Creates `apps/SandboxApi/.env` from `.env.example`, replacing each
   `tobemodified` with `randomBytes(16).toString('base64')`. If `.env` already
   exists, its secrets are left alone.
2. Repairs an empty `DATABASE_FILENAME` (the scaffold bug from 2.4).
3. Creates the directory holding the sqlite file, which sqlite will not do.

`predev` and `pretest:e2e` both call it, so nobody has to remember.

## Part 7 — The spec-driven flow

The last piece is the workflow the repo is developed with. Full explanation in
[`how-to-spec-drive.md`](./how-to-spec-drive.md); the files to create are:

```
specs/templates/spec.md       # what and why
specs/templates/plan.md       # how
specs/templates/tasks.md      # in what order
scripts/new-spec.mjs          # scaffolds specs/NNNN-slug/ from the templates
scripts/check-specs.mjs       # gates a spec against its status
CLAUDE.md                     # points Claude Code at the flow
.claude/commands/spec-*.md    # /spec-new, /spec-plan, /spec-tasks, …
```

Both scripts are plain Node with no dependencies. `check-specs.mjs` tightens
its checks as a spec's status advances — a `Draft` is not punished for being
incomplete, while a `Shipped` spec cannot have unanswered questions or unticked
tasks.

Write the first spec last, describing the setup you just built. That is
`specs/0001-monorepo-foundation/`, and it doubles as the worked example
everyone reads before writing their own.

## Troubleshooting

**`SqliteError: unable to open database file`**
`DATABASE_FILENAME` is empty in `apps/SandboxApi/.env`, or `apps/SandboxApi/.tmp/`
does not exist. Run `npm run setup`; see 2.4 for why.

**The SPA loads at `/app` but every asset 404s**
`base: '/app/'` is missing from the SPA's Vite config. Check whether
`apps/SandboxApi/public/app/index.html` references `/assets/…` instead of
`/app/assets/…`, and rebuild.

**A client-side route 404s on refresh, but `/app/` works**
The `spa-fallback` middleware is missing, or sits below `strapi::public` in
`config/middlewares.js`. It must be directly above it.

**`npm run build:spa` leaves an empty `public/app`**
`emptyOutDir: true` is missing, so Vite refused to write outside its root.

**A prototype shows on the dev entry page but 404s in the build**
`rollupOptions.input` is not picking it up. It only includes `*.html` files
under `prototypes/`, and the list is computed when Vite loads its config —
restart the build after adding a file in a new location.

**`Executable doesn't exist at /…/chrome-headless-shell`**
Playwright's browser is not installed. Run `npm run e2e:install`, or point
`E2E_CHROMIUM_EXECUTABLE` at a Chromium the machine already has.

**Port already in use**
Every server uses `strictPort`, so a clash fails loudly rather than drifting to
another port and breaking the test base URLs. Free the port, or override it:
`VITE_DEV_PORT`, `VITE_PREVIEW_PORT`, or `PORT` for Strapi.

**Strapi admin build fails after adding a React dependency**
Strapi's admin runs React 18 and the SPA runs React 19; npm nests one of them.
Re-run `npm install` at the root and rebuild. If it persists, delete
`node_modules` and the lockfile and install again.
